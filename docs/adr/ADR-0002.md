## 1. Contexto
- Problema: Necesidad de garantizar transacciones ACID para registros de productos críticos, acciones comerciales y KPIs.
- Restricciones: Integración con ERP y Vector DB para recuperación semántica.
- Fuerzas en tensión: Consistencia vs rendimiento, costo vs complejidad de mantenimiento.
- Lo que se sabe: Los datos críticos deben ser confiables y auditables.
- Lo que se desconoce: Escalabilidad horizontal exacta necesaria para pico máximo de usuarios.

## 2. Alternativas consideradas
| Alternativa | Pros | Contras |
|-------------|------|---------|
| PostgreSQL | ACID, soporte transaccional, consultas SQL estables | Escalabilidad horizontal limitada |
| DynamoDB | Escalabilidad y alta disponibilidad | Transacciones más complejas, curva de aprendizaje |

## 3. Decisión
> Elegimos **PostgreSQL** como persistencia principal para asegurar transacciones confiables y consistencia de datos críticos en la aplicación.

## 4. Consecuencias
### Positivas
- Integridad de datos y transacciones confiables.
- Historial completo de registros y acciones.
### Negativas / Costos
- Escalabilidad vertical limitada.
- Mayor gestión de bases de datos y backups.
### Neutras / Observables
- La arquitectura hexagonal permite intercambiar base de datos en el futuro si se requiere.

## 5. Impacto en el sistema
- Código: repositorios y adaptadores apuntan a PostgreSQL.
- Operaciones: requiere administración de instancias, backups y monitorización.
- Seguridad: cifrado y control de accesos.
- Equipo: capacitación mínima en SQL y optimización de queries.
- Costo: infraestructura y licencias según plan de AWS o local.

## 6. Plan de reversión
- Señales: errores de integridad, retrasos en transacciones.
- Plan B: migrar temporalmente a DynamoDB o base SQL alternativa mientras se corrigen problemas.
- Costo estimado: medio, requiere scripts de migración.

## 7. Validación
- Pruebas de integridad y consistencia de datos.
- Stress test con 10k usuarios concurrentes simulados.
